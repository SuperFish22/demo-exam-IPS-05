От ER к базе данных: таблицы, импорт и запрос

ER-диаграмма — чертёж. Теперь по нему нужно построить настоящую базу в PostgreSQL, заполнить её данными заказчика и научиться задавать ей вопросы. Ниже всё по шагам, а в конце песочница, где можно потренироваться прямо в браузере.

Две половины SQL

Описание структуры (DDL)

CREATE TABLE, ALTER TABLE, DROP TABLE. Создаём «шкаф с ящиками»: какие таблицы, какие поля, какие правила.

Работа с данными (DML)

INSERT кладёт строки, UPDATE меняет, DELETE удаляет, SELECT достаёт. Работаем с тем, что лежит в ящиках.

В каком порядке создавать таблицы

Таблица, на которую ссылаются, должна появиться раньше той, что ссылается. Нельзя создать customer_orders с внешним ключом на counterparties, если counterparties ещё нет: PostgreSQL ответит ошибкой «relation does not exist». Поэтому порядок такой: сначала справочники без ссылок (units, counterparty_types, roles), потом справочники со ссылками (counterparties, nomenclature), потом документы (customer_orders), и в конце строки документов. С данными то же самое: сначала заполняем справочники, потом документы.

Аналогия

Нельзя прибить полку к стене, которой ещё нет. Сначала стены (справочники), потом полки (документы), потом то, что на полках (строки).

Почему не float для денег

Типы real и double precision хранят числа приблизительно. 0,1 + 0,2 в них равно 0,30000000000000004. Для одной суммы незаметно, а в отчёте по тысяче строк копейки «поплывут». numeric хранит число точно, как записано.

Ограничения: правила, которые проверяет сама база

Ограничения — это охранники у входа в таблицу. Они не пустят неправильные данные, даже если в программе ошибка. Чем больше правил вы опишете в базе, тем меньше мусора в ней окажется.

ОграничениеЧто означаетПример
PRIMARY KEYУникальный и обязательный номер строкиid integer ... PRIMARY KEY
NOT NULLПоле нельзя оставить пустымУ заказа обязательно есть дата
UNIQUEДвух одинаковых значений быть не можетЛогин пользователя

REFERENCESВнешний ключ: значение должно существовать в другой таблицеcustomer_id ... REFERENCES counterparties (id)

GENERATED BY DEFAULT AS IDENTITY означает «база сама выдаёт следующий номер». При вставке поле id можно не указывать.

Создание таблиц (PostgreSQL)

Показать schema.sql для «Вершины» 
CREATE TABLE units (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name varchar(20) NOT NULL UNIQUE
);

CREATE TABLE counterparty_types (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name varchar(30) NOT NULL UNIQUE
);

CREATE TABLE counterparties (
    id varchar(9) PRIMARY KEY,
    name varchar(255) NOT NULL,
    inn varchar(12),
    address varchar(255),
    phone varchar(20),
    counterparty_type_id integer NOT NULL REFERENCES counterparty_types (id)
);

CREATE TABLE nomenclature_types (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name varchar(30) NOT NULL UNIQUE
);

CREATE TABLE nomenclature (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code varchar(20),
    name varchar(255) NOT NULL UNIQUE,
    unit_id integer NOT NULL REFERENCES units (id),
    nomenclature_type_id integer NOT NULL REFERENCES nomenclature_types (id),
    price numeric(12, 2) NOT NULL CHECK (price >= 0)
);

CREATE TABLE operations (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code varchar(20),
    name varchar(255) NOT NULL UNIQUE,
    price numeric(12, 2) NOT NULL CHECK (price >= 0)
);

CREATE TABLE specifications (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id integer NOT NULL REFERENCES nomenclature (id),
    name varchar(255) NOT NULL
);

CREATE TABLE specification_materials (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    specification_id integer NOT NULL REFERENCES specifications (id) ON DELETE CASCADE,
    material_id integer NOT NULL REFERENCES nomenclature (id),
    quantity numeric(12, 3) NOT NULL CHECK (quantity > 0),
    UNIQUE (specification_id, material_id)
);

CREATE TABLE specification_operations (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    specification_id integer NOT NULL REFERENCES specifications (id) ON DELETE CASCADE,
    operation_id integer NOT NULL REFERENCES operations (id),
    time_norm numeric(8, 2) NOT NULL CHECK (time_norm > 0),
    quantity integer NOT NULL DEFAULT 1
);

CREATE TABLE customer_orders (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    number integer NOT NULL,
    order_date date NOT NULL,
    customer_id varchar(9) NOT NULL REFERENCES counterparties (id),
    UNIQUE (number, order_date)
);

CREATE TABLE customer_order_items (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_order_id integer NOT NULL REFERENCES customer_orders (id) ON DELETE CASCADE,
    product_id integer NOT NULL REFERENCES nomenclature (id),
    quantity numeric(12, 3) NOT NULL CHECK (quantity > 0),
    price numeric(12, 2) NOT NULL,
    discount_sum numeric(12, 2) NOT NULL DEFAULT 0
);

CREATE TABLE roles (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name varchar(30) NOT NULL UNIQUE
);

CREATE TABLE users (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    login varchar(50) NOT NULL UNIQUE,
    password varchar(100) NOT NULL,
    role_id integer NOT NULL REFERENCES roles (id),
    is_blocked boolean NOT NULL DEFAULT false,
    failed_attempts integer NOT NULL DEFAULT 0
);

Импорт контрагентов из JSON одним запросом

Откройте Заказчики.json, скопируйте всё содержимое и вставьте его между кавычками вместо многоточия. PostgreSQL сам разберёт массив.

INSERT INTO counterparty_types (name) VALUES ('Поставщик'), ('Покупатель');

INSERT INTO counterparties (id, name, inn, address, phone, counterparty_type_id)
SELECT j ->> 'id',
       j ->> 'name',
       NULLIF(j ->> 'inn', ''),   -- пустая строка превращается в NULL
       j ->> 'addres',            -- в файле опечатка, в базе поле address
       j ->> 'phone',
       t.id
FROM json_array_elements('[ ...содержимое файла... ]'::json) AS j
JOIN counterparty_types AS t ON t.name = j ->> 'type';

Разбор по строчкам

  1. '[ ... ]'::json Текст файла превращаем в значение типа JSON. Два двоеточия в PostgreSQL означают «привести к типу».
  2. json_array_elements(...) AS j Разворачивает массив в строки: было одно значение с шестью объектами, стало шесть строк, в каждой один объект. Каждую строку называем j.
  3. j ->> 'name' Достаёт из объекта значение по ключу как текст. Стрелка с одной угловой скобкой (->) вернула бы JSON, с двумя (->>) — обычный текст, который можно положить в varchar.
  4. NULLIF(j ->> 'inn', '') Если ИНН — пустая строка, вместо неё будет NULL. Пустая строка и «значение отсутствует» — разные вещи, и для отсутствия в SQL есть NULL.
  5. JOIN counterparty_types AS t ON t.name = j ->> 'type' В JSON тип записан словом «Покупатель», а в нашей таблице нужен номер типа. Соединяем по названию и берём t.id. Поэтому таблицу типов заполняем первой строкой скрипта.
Если импортировалось меньше строк, чем в файле

Скорее всего, у части записей тип написан иначе («поставщик» с маленькой буквы, лишний пробел), и JOIN их не нашёл. Проверьте: SELECT DISTINCT j ->> 'type' FROM json_array_elements('…'::json) AS j;

Если в тексте JSON встречается одинарная кавычка, удвойте её. Excel-файлы удобнее сохранить в CSV и загрузить в DBeaver: правой кнопкой по таблице → «Импорт данных» → CSV.

Запрос полной стоимости заказа (модуль 3)

Задача: посчитать стоимость всех материалов на заказ с учётом количества изделий и норм расхода. Для заказа на 2 стола ответ 9 974,28 ₽. Длинный запрос с пятью JOIN пугает, но собирается он по шагам, и на каждом шаге можно посмотреть промежуточный результат.

Как думать о JOIN

JOIN — это «пришить к каждой строке подходящую строку из другой таблицы». Начинаем с одной таблицы и шаг за шагом пришиваем к ней то, чего не хватает, пока в строке не окажутся все числа для расчёта. Для стоимости материала нужны три числа: сколько изделий заказали, сколько материала на одно изделие и сколько стоит материал.

  1. Начинаем с заказа. 
    SELECT co.number, co.order_date
FROM customer_orders AS co
WHERE co.number = 1;
    Одна строка: заказ № 1. AS co — короткое имя таблицы, чтобы не писать её название целиком.
  2. Пришиваем строки заказа: узнаём, что и сколько заказали. 
    JOIN customer_order_items AS coi ON coi.customer_order_id = co.id
    Теперь в строке есть coi.product_id (стол) и coi.quantity (2).
  3. Пришиваем спецификацию этого изделия. 
    JOIN specifications AS s ON s.product_id = coi.product_id
    Нашли «рецепт» стола.
  4. Пришиваем строки спецификации: материалы и нормы. 
    JOIN specification_materials AS sm ON sm.specification_id = s.id
    Здесь одна строка заказа «размножилась» в пять: по одной на каждый материал стола. В каждой есть норма sm.quantity.
  5. Пришиваем материал, чтобы узнать цену. 
    JOIN nomenclature AS n ON n.id = sm.material_id
    Теперь в каждой из пяти строк все три числа: 2 стола, норма, цена.
  6. Считаем и складываем. Стоимость одной строки: coi.quantity * sm.quantity * n.price. Сумма по всем строкам: SUM(...). Поскольку в SELECT есть и обычные поля (номер, дата), их надо перечислить в GROUP BY: так SQL понимает, по какому признаку собирать строки в группу.

Показать запрос целиком 
SELECT co.number,
       co.order_date,
       c.name AS customer_name,
       SUM(coi.quantity * sm.quantity * n.price) AS materials_cost
FROM customer_orders AS co
JOIN counterparties AS c ON c.id = co.customer_id
JOIN customer_order_items AS coi ON coi.customer_order_id = co.id
JOIN specifications AS s ON s.product_id = coi.product_id
JOIN specification_materials AS sm ON sm.specification_id = s.id
JOIN nomenclature AS n ON n.id = sm.material_id
WHERE co.number = 1
GROUP BY co.number, co.order_date, c.name;
Частые ошибки
  • Забыли умножить на количество изделий. Получится стоимость одного стола: 4 987,14.
  • Соединили по названию, а не по id. Работает, пока в названиях нет опечаток. На экзамене они есть.
  • «column must appear in the GROUP BY clause». В SELECT есть поле без агрегатной функции, которого нет в GROUP BY. Добавьте его туда.
  • Число в 1000 раз больше. Перепутали единицы: считали винты штуками, а цена за тысячу.

SQL-песочница

В браузере работает учебная база «Вершины» с данными из документов. Это SQLite, а не PostgreSQL, но SELECT, JOIN, GROUP BY, UPDATE работают так же. Изменения живут до перезагрузки страницы, поэтому ломать базу не страшно.

Как заниматься
  1. Выберите задачу и прочитайте условие.
  2. Сначала посмотрите на таблицы: SELECT * FROM имя_таблицы;. Так понятнее, что где лежит.
  3. Пишите запрос по шагам и запускайте после каждого JOIN.
  4. Застряли — нажмите «Подсказка». Решение смотрите в последнюю очередь.
  5. «Проверить ответ» сравнивает ваш результат с эталоном: те же строки и те же столбцы в том же порядке.
